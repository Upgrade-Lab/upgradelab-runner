# ADR 0001: What UpgradeLab adds over existing tools

Status: accepted, 2026-10-07. Based on the pages and READMEs below, read on that date. None of the tools was installed or executed for this ADR, and a README describes intent, not tested behavior. Absence from a README is not proof that a feature does not exist.

## What I read, and what it says

- **Stellar docs, "Migrate contract storage"** (developers.stellar.org/docs/build/guides/storage/migrate-contract-storage). Names the real failure: when a contract's stored data structure gains fields, old ledger entries make the new code trap if they are read as the new type. It describes two patterns, a versioned enum that converts on read (lazy migration) and a version marker stored next to the data (lazy or eager), and says eager migration rarely scales to large datasets because of instruction and ledger-entry limits. It warns that reading old entries directly as the new type traps (`UnexpectedSize`), that `try_from_val` does not recover because the host traps before returning `Err`, and that old version branches must not be removed while legacy data exists. It tells you how to write a migration. It does not provide a way to rehearse one.
- **Stellar docs, state archival** (developers.stellar.org/docs/learn/fundamentals/contract-development/storage/state-archival). Temporary entries are deleted at TTL 0 and cannot be restored; persistent and instance entries are archived and restorable. From Protocol 23 archived entries named in a transaction's restore list (normally filled in by simulation) are restored automatically before the invocation, and `RestoreFootprintOp` remains for manual control. The RPC simulation returns a `restorePreamble`. Consequence for this project: balances live in persistent storage, never temporary, and the in-process runner does not model archival (see below).
- **Crucible** (github.com/benelabs/crucible README). A Rust testing library wrapping the soroban-sdk test utilities: a fluent environment builder, pre-funded named accounts, mock tokens, event assertion macros, cost tracking, ledger checkpoints and rollback, property-based fuzzing, and cross-contract tests in one environment. The README has no discussion of contract upgrades or migrations. It is a general test toolkit you write tests with; it supplies no upgrade scenario, no old-to-new WASM flow and no named migration invariants.
- **soroban-upgrade-safeguard** (github.com/ShippedLabs/soroban-upgrade-safeguard README). A Rust CLI that compares two WASM builds by parsing the `contractspecv0` custom sections, decoding the XDR and doing a structural comparison, to flag breaking changes before deployment: storage layout (removed, reordered or retyped fields), function signatures, event schemas and cascading type impacts. It reports severities and exit codes in several formats and states limits such as a 500-pair manifest cap. It is a static interface and layout comparison. As described it does not execute either WASM, so it cannot show whether a migration function preserves a balance or whether the upgrade call is authorized.
- **OpenZeppelin Stellar contracts, upgradeable utility** (docs.openzeppelin.com/stellar-contracts/utils/upgradeable, and the stellar-contracts README). Provides a standardized `Upgradeable` upgrade entry point and generated client, deliberately no migration trait (migrations vary too much), three documented migration patterns (eager for bounded data, lazy with version markers for unbounded data, enum wrapper), an auxiliary `Upgrader` contract that wraps upgrade and migration in one transaction, and a mention of rollback by upgrading again. The docs contain no discussion of testing a migration. It is building blocks for writing the upgrade path, not a harness for rehearsing it.

## The gap, stated narrowly
Each tool above helps with writing the upgrade (Stellar guide, OpenZeppelin), with testing contract logic in general (Crucible), or with statically diffing two builds (soroban-upgrade-safeguard). From what I read, none of them takes an application team's own seed operations, deploys the actual old compiled WASM, performs the real `update_current_contract_wasm` upgrade, runs the migration calls against the seeded state, and judges named invariants about that state with real authorization checks. That executable, application-driven rehearsal with a replayable report is what UpgradeLab adds. It complements the others: run the static diff first, write the migration with the guide's patterns or OpenZeppelin's, rehearse it here. Teams may well have private migration tests; this makes no novelty claim.

## Decision
Build a runner that treats the old WASM, the new WASM, the seed operations, the probes and the invariants as inputs, executes them, and writes a versioned, replayable report; and a static viewer for those reports. Do not build a static analyzer (soroban-upgrade-safeguard exists), a test DSL (Crucible exists) or migration helpers (the Stellar guide and OpenZeppelin cover patterns).

## Consequences
- Invariants are only as good as the scenario author's seed state and probes. The runner never clones live storage and does not discover storage keys: it reads exactly what the scenario names.
- The execution environment is an in-process Soroban host, not a network (ADR 0002), so results say "this scenario held in the host", not "this upgrade is safe on mainnet".
- No contract-security expert has reviewed the invariants or the fixture. The vault is a teaching fixture, not an audited design.
